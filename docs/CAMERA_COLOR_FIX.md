# 拍照偏色与过亮修复记录

日期：2026-10-25。设备：`maixcam2-test-device`，MaixPy 4.12.5。用户反馈同时存在偏色与明暗异常；修复部署后，用户现场反馈“刚才看到图片颜色正常了”。

## 定位结果

原 `_capture_jpeg()` 每次新建相机并保存第 8 次读取的图像，实际只丢弃了前 7 帧。诊断中第 8 帧在打开相机后约 0.292 秒取得，画面明显偏亮、颜色发白；同一次打开继续读取到第 30 帧后，亮度和颜色稳定很多。

| 样本 | 打开后经过时间 | 全图 RGB 均值 | 任一通道≥250的像素占比 |
| --- | --- | --- | --- |
| 原取帧点：第 8 帧 | 0.292 s | 171.88 / 164.35 / 157.35 | 12.82% |
| 第 30 帧 | 0.890 s | 134.73 / 126.33 / 120.63 | 0.59% |
| 第 60 帧 | 1.457 s | 134.71 / 126.35 / 120.63 | 0.60% |
| 第 120 帧 | 2.590 s | 134.80 / 126.53 / 120.78 | 0.62% |

这个占比是接近通道饱和的描述性指标，不等同于严格的过曝面积或色彩准确度测量。最有力的对照来自同一次打开、同一场景的连续帧，而不是跨时间不同构图的比较。

初始 AE 与 AWB 均为 Auto；显式重设自动模式后，第 8 帧仍偏亮，说明只设自动模式不能替代预热。证据支持“启动自动成像尚未稳定时过早保存”，而不是需要硬编码一个曝光时间。

## 排除的路径

- 同帧保存 PNG 与 JPEG quality=80，全图平均绝对差约 1.8–2.8 灰度值，各 RGB 通道均值差小于 0.1；没有严重编码偏色的证据。
- SDK 创建红、绿、蓝色块，PNG 中心分别为 (255,0,0)、(0,255,0)、(0,0,255)；JPEG 分别约为 (254,0,0)、(0,255,1)、(0,0,254)，未见红蓝互换。
- 修复后的真实 MCP 预览与实际显示合成帧的采样匹配率为 100%（每通道允许1灰度值误差）；显示链路没有把这张 JPEG 换成另一种配色。
- exposure()/gain() 的读值仅作为诊断元数据保留，不据此判定实时 AE 收敛。当前公开 CDK 实现的 getter 有读取手动参数的版本边界，不能仅靠这些数值下结论。

## 修改

仅修改 `xiaozhi/service/hardware_tools.py` 的相机取帧流程，并新增对应测试：

1. 创建相机后明确启用 `camera.AeMode.Auto`、`camera.AwbMode.Auto`。
2. 持续读取新帧，同时满足 **至少30帧、至少2秒** 后才保存最终 JPEG。
3. 预热读帧预算为5秒，每次 `read` 的超时不超过剩余预算；超时或无帧明确失败并关闭相机。
4. 不设置固定曝光、增益、白平衡系数，不交换颜色通道，不对照片做调色。

相机初始化、编码及网络分析不包含在这5秒预热读帧预算中。JPEG质量、上传协议、底部MCP名称和拍照后3秒预览均保留。

## 修复后验证

- 新增四项回归先红后绿：自动模式、快速读帧的时间门槛、慢速读帧的帧数门槛、超时关闭。
- 完整主机与板端 Python 测试各 **41项通过**。
- 三次冷启动使用修改后的实际函数取得 JPEG，包含打开/预热/保存/关闭的总耗时分别为 **2.662、2.549、2.659秒**。
- 三张修复样本的通道饱和占比分别为 **0.78%、0.92%、0.79%**，没有重现旧第8帧的明显发白；人物动作与取景有小变化，不能把该数字当作严格的跨图色彩误差对照。
- 实际小智 `self.camera.take_photo` 返回成功，视觉分析与语音回复继续工作。
- 最后一次预览采样记录约 **3.099秒**，预览区与实际合成帧匹配率100%，消失后约0.04%；用户现场确认图片颜色正常。

第一次回归抓到的“预览中”屏幕帧没有照片，保留为 `live_test-first.output.txt` 和首次图片，没有用于宣称显示通过。再次记录抓帧耗时并检查实际合成图后取得上述成功证据；本轮没有进一步修改显示代码。

拍照取图会比旧版多等待约1–2秒，用来等待自动成像稳定；照片显示时长仍为3秒。尚未用标准色卡/色度计做光学色准校准，也未覆盖所有极暗、频闪或瞬时切换光源的场景。
