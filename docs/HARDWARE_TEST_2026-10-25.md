# 小智与 MaixCAM2 实机测试记录

> 本文是摄像头/补光灯接入前的历史测试快照；同日后续已完成 MCP 接入，当前结果见 [接入验收记录](CAMERA_LIGHT_MCP_VALIDATION.md)。

日期：2026-10-25（Asia/Taipei）。基线：`9d7885ee46329ac5a5daebd418e3a62f8c2f4f39`。

用户授权测试设备现有功能，包括摄像头、补光灯、屏幕、扬声器、麦克风。测试实际连接设备执行，临时调整开关和音量，并在独立硬件阶段暂停、恢复服务。未更改产品源码、安装依赖或刷机。

## 环境与方法

- Ubuntu 22.04，Python 3.13.2，MaixPy 4.12.5；USB SSH 可用。
- 小智依赖及模型在前一轮检查中已核实；设备代码与本地基线一致（文本比较忽略 CRLF）。
- 使用现有 `/tmp/xz_inwav`、`xz_call`、`xz_stop`、`xz_cmd` 和 `ovl_dump_b` 调试入口；没有向运行服务注入新功能。
- 中文测试音频由 Windows 本地语音合成生成，16 kHz / 16 位 / 单声道。注入测试绕过真实麦克风，单独标记。
- 独立硬件测试先停止小智，再停止 launcher；测试进程退出后恢复 launcher，随后恢复小智，避免同时创建多个 Recorder。
- 屏幕证据为注入层输出的 640×480 BGRA 合成帧；用户另行确认实际声音与屏幕文字正常。

音频回环分析：700 Hz 播放段相对静音段同频带功率提高约 31.3 dB，1300 Hz 提高约 43.6 dB。原始测试脚本用 RMS>100 的固定阈值时，700 Hz 被判 false（实测 RMS 约 64–69），但频谱连续明确落在 700 Hz；保留原始结果，补充相同频带的基线对照分析，不将任意 RMS 阈值解释成麦克风故障。

第二轮固定问句的 TTS 下行记录约 19–20 ms 平均帧间隔，单句最大 30–41 ms；相关 stats 窗口累计丢帧和播放欠载为 0。这些是短时服务内部指标，不是口到耳端到端延迟或长期验收。

## 测试中发现的限制与问题

1. **小智没有摄像头/补光灯 MCP 接口。** 硬件能独立工作，当前产品功能仍缺少接入。
2. **配置被后台反复写入。** 恢复空闲后只读观察 3 秒，config.json mtime 改变 11 次。源码的配置热加载会调用 `load_cfg()`，而该函数又执行 `save_cfg()`，形成持续重写。测试中一次连续开关设置未生效，配置覆盖竞争是待进一步验证的原因；重新写入并等待配置与 state 同时确认后，禁止弹窗测试通过。本轮未修复。
3. **首轮测试音频衔接不充分。** 紧接上一轮注入时，屏幕工具收到“你好！”而非指定文字。调整测试流程，等待上一段注入尾部静音与播放队列排空后，复测准确显示“硬件测试成功”。不把首轮偏差直接归因为产品识别错误。
4. **独立硬件脚本初次使用了过时的整数曝光模式参数。** 设备实际接口要求 `camera.AeMode.Manual`。修正测试脚本后摄像头、PWM、音频回环完成；第一次失败仍留档，不算硬件损坏。
5. **额外声学唤醒复现未完成。** 尝试在小智运行时从独立进程播放唤醒词，aplay 报默认音频设备不存在，独立 PyAudio 报没有默认输出设备；未形成新的声学唤醒证据。未据此断言独占冲突，因为缺少进一步设备/运行环境对照。现有小智播放与停止服务后的独立回环均正常。
6. 长时间稳定性、断网恢复、冷启动循环、噪声/距离下唤醒率、声学识别准确率、设置 App 每个触控控件，以及 IMU、蓝牙和外部扩展接口没有做完整验收。摄像头 NPU/AI 推理也不在本轮已通过项中。

## 恢复与最终核对

- `enabled=false`（恢复原来的关闭状态）。

- `muted=false`、会话 `idle`、弹窗无可见像素。
- launcher 与 xiaozhi 均 `active/running`，本次恢复后的 `NRestarts=0`。
- 补光灯已关闭，PWM6 通道 unexported。
- 重新核对服务、UI 渲染、设置 App、注入层源码和 systemd unit 的规范化 SHA256，产品文件与测试前一致。

独立硬件阶段确实进行了计划内服务停止/启动，不能把 `NRestarts=0` 理解成整个测试未重启服务。
